# 02 — Technical SEO

Crawling, indexing and rendering. These are the failures that cost the most, and they're invisible in a browser. Every prompt asks for evidence, because in this area "should be fine" is how outages ship.

---

### Review and rewrite robots.txt

**Use when:** before a launch, after a migration, or whenever someone has touched robots.txt.

```text
Act as a technical SEO who knows RFC 9309 exactly. Review this robots.txt for {{domain}}.

Check:
- group semantics: each crawler obeys ONE group (its most specific match). Rules from * are not merged into a named group.
- longest-match wins; Allow wins ties; paths are prefixes, case-sensitive; * and $ wildcards
- render-critical paths (JS/CSS/images) that are blocked
- locale-prefixed copies of every Disallow (/tr/panel as well as /panel)
- no URL that should carry noindex is Disallowed (a blocked URL's noindex is never seen)
- Bingbot, Applebot and other search engines aren't blocked by accident; no Crawl-delay throttling Bing
- a deliberate AI policy: training bots vs AI-search bots vs user-triggered fetchers, plus an optional Content-Signal line
- an absolute Sitemap: line

Output: a table of each important crawler (Googlebot, Bingbot, Applebot, YandexBot, GPTBot, OAI-SearchBot, ClaudeBot, Claude-SearchBot, PerplexityBot, Google-Extended) → allowed or blocked at / and at {{key_path}}. Then the problems, then a corrected file with a comment per section.
Private routes to block: {{/admin /dashboard /api}}. AI decision: {{allow AI search, block training | allow all | block all}}.

robots.txt:
{{paste}}
```

### Generate or fix the XML sitemap

**Use when:** the sitemap is missing, stale, or lists URLs it shouldn't.

```text
Act as a technical SEO engineer. Build (or fix) the XML sitemap for this {{framework}} project.

Rules:
- list exactly the public-index URLs: absolute, canonical, 200, not noindex, not Disallowed
- split at 50,000 URLs / 50 MB uncompressed and add a sitemap index
- <lastmod> only from a real content-change timestamp (W3C format). Never the build time.
- no <priority> or <changefreq> (Google ignores them)
- hreflang via xhtml:link if the site is multilingual
- reference it from robots.txt with an absolute Sitemap: line

Give me the generator code that fits the project's routing, then a verification command that fetches the sitemap and checks a sample of 20 URLs for 200 + self-canonical + no noindex.
Data source for URLs and timestamps: {{database table / CMS / filesystem}}.
```

### Hunt soft 404s, template by template

**Use when:** Search Console reports "Soft 404", or after adding loading states or Suspense boundaries.

```text
Find every route template in this project that can answer 200 for a URL that doesn't exist.

For each dynamic route ([slug], :id, catch-all):
1. Read the route code: what happens when the entity lookup fails?
2. Prove it. Request {{base_url}}/<template-root>/seo-check-nonexistent-123 and record the status code.
3. In Next.js App Router specifically, look for a loading.tsx or Suspense boundary above the segment. It flushes a 200 shell before notFound() runs, so the refusal has to happen in layout.tsx or before streaming starts.

Output: a table of template → current status for a missing entity → fix → verification command. Then wire the template roots into the deploy check:
SEO_SMOKE_404_PATHS="{{/blog /products /users}}" bash tools/seo-smoke.sh {{base_url}}
```

### Untangle a canonical / duplicate cluster

**Use when:** Search Console says "Duplicate, Google chose different canonical", or several URLs show the same content.

```text
Act as a technical SEO. These URLs show the same or near-identical content:
{{list of URLs}}

For each URL, collect the five signals and show them in a table: status code, rel=canonical, sitemap membership, how internal links point to it, redirects, and hreflang if any.
Find where the signals disagree. Then choose ONE canonical URL per cluster and give me the changes that align all five signals on it: 301s for true duplicates, self-canonicals, sitemap entries, internal links and hreflang.
Parameters to keep crawlable vs to consolidate: {{?page= keep, ?utm_ consolidate, ?sort= consolidate}}.
Never "fix" a variant with noindex when a canonical or a 301 is the right instrument.
```

### Build a migration redirect map

**Use when:** changing domain, URL structure or platform.

```text
Act as a site-migration lead. We are moving from {{old setup}} to {{new setup}} on {{date}}.

1. Build the URL inventory from the union of: a crawl, the sitemaps, a Search Console pages export, analytics landing pages and server logs. Tell me which of these you could actually use.
2. Write the 1:1 redirect map as CSV (old,new), generated by rules plus an exceptions list. No chains, no blanket redirects to the homepage, and a 410 where no equivalent page exists.
3. Give me a script that tests the whole map (status 301 and the exact target), and a day-0 checklist: robots.txt, noindex scan, sitemaps (old and new), Change of Address, internal links.
4. Write down the rollback triggers now, before launch.
URL rules: {{e.g. /blog/:id → /articles/:slug}}
```

### Build and verify hreflang

**Use when:** the site is multilingual, or international traffic goes to the wrong locale.

```text
Act as an international SEO engineer. Locales: {{en, tr, de}} using {{subdirectory /tr/ | subdomain | ccTLD}}. Fallback: {{en}}.

1. Implement hreflang in the project's metadata layer. Every page lists itself and every other language version, plus x-default, as absolute URLs with valid ISO codes (en-GB, not en-UK; no underscores).
2. Each locale version's canonical points to ITSELF, never to the default language.
3. Make sure there's no automatic IP or Accept-Language redirect. Offer a banner or selector instead.
4. Set <html lang> per locale (Bing reads it).
5. Verify reciprocity: for one page per template, fetch every alternate and confirm that each one links back. One-way sets are discarded entirely.
Show the code change and the verification output.
```

### Diagnose JavaScript rendering problems

**Use when:** pages are "Crawled – currently not indexed", or AI answer engines never quote you.

```text
Act as a JavaScript SEO specialist. For these routes of a {{framework}} app: {{routes}}

1. Fetch the RAW HTML, with no JavaScript (curl -A "Googlebot" {{url}}). Is the page's main content there: its H1, its body text, and its internal links as <a href>?
2. Compare it with the rendered DOM. List what exists only after JavaScript runs.
3. Check the raw HTML (not the hydrated DOM) for <title>, canonical and robots. Note any metadata that is streamed after </head>.
For each gap, give the fix: move the data fetch server-side (SSR/SSG/ISR), render pagination as real links, and stop using client-only metadata.
Remember that most AI crawlers never execute JavaScript, so whatever is missing from the raw HTML is invisible to them.
```

### Diagnose Core Web Vitals

**Use when:** Search Console's Core Web Vitals report is red, or PageSpeed field data fails.

```text
Act as a web performance engineer. Field data (CrUX / Search Console) for {{url or URL group}}:
LCP {{x}}s, INP {{y}}ms, CLS {{z}}, TTFB {{t}}ms (diagnostic only).

Working from the page source and the framework ({{framework}}):
- LCP: which element is it? Is it discoverable in the raw HTML (real src, not data-src), eager, and fetchpriority=high? Is TTFB the real cause?
- INP: long tasks over 50 ms, hydration cost, third-party scripts. Suggest yield points and code-splitting.
- CLS: images or embeds without reserved space, late-injected banners, web fonts.
Rank the fixes by expected impact. Treat lab tools (Lighthouse) as debugging aids only: ranking uses the 28-day CrUX field data, so say how the result will be confirmed there.
```

### Design a faceted-navigation policy

**Use when:** filters and sorting create thousands of URLs (e-commerce, listings, directories).

```text
Act as a technical SEO for a large catalog. Filters: {{list facets, e.g. color, size, brand, price, sort}}.
For each facet and each combination type, decide: index or not, and how to implement it.
- Facets with real search demand and unique content → a static path, with their own title, H1 and description, listed in the sitemap.
- Rare combinations → noindex,follow, or robots.txt.
- Sort and view parameters → canonical to the base URL, plus robots.txt.
- Pagination → self-canonical, crawlable.
Also: a normalized parameter order, a noindex plus a helpful alternative on empty-result pages, and an estimate of the crawl space before and after.
Output: a policy table, and the code or config changes for {{framework}}.
```

### Crawl-budget analysis from server logs

**Use when:** the site has more than about 10,000 URLs and important pages are crawled rarely.

```text
Act as a crawl-budget analyst. Here is a sample of access logs (combined format):
{{paste or attach logs}}

1. Keep only verified search crawlers. Note that user agents can be spoofed and say how to verify them by reverse DNS.
2. Report the status-code mix per crawler (Googlebot, Bingbot, YandexBot, Applebot, AI bots).
3. Show the top 50 crawled paths, grouped by template. Is crawl budget being spent on parameters, facets or redirects?
4. List sitemap URLs that were never crawled in the period.
5. Report response time and the 5xx/429 rate.
Give the 3 changes that would move the most crawl toward valuable URLs.
```
